# МЫС Mesh — этапы 2–3: интернет-узлы, выбор пути, Android-радио

Дата: 2026-10-24. Продолжение `2026-10-23-mys-mesh-core-design.md` (этап 1 — ядро).
Решения владельца те же: живой маршрут, открытая ретрансляция (выключается), те же
P2P-каналы, маршрутизация по запросу, стартовые узлы + обмен соседями; рядом —
BLE (фон, по умолчанию) и Wi-Fi Direct (пока открыт раздел «Mesh»).

## Этап 2. Интернет-узлы и выбор пути

### Провод WebSocket

Интернет-линк — WebSocket (`wss://…/mesh`, проходит прокси и NAT как обычный HTTPS).
Одно бинарное WS-сообщение = один кадр линка (без своего префикса длины),
≤ `MAX_FRAME`. Поверх — то же шифрование линка (crypto_kx + secretstream).

- Десктоп: `WsWire` (`websockets`), клиент.
- Телефон: `WsWire` (OkHttp `WebSocket`), клиент.
- Телефоны и обычные десктопы входящих не принимают (NAT) — интернет-mesh строится
  вокруг публичных узлов.

### Публичный узел на сервере

- Отдельный процесс `mesh_daemon.py` (asyncio, код ядра вендорится в
  `vsc_web/mesh/` из `vsc_desktop/src`), слушает `127.0.0.1:7811` кадрами `TcpWire`.
  Ретрансляция включена, свои поиски не ведёт.
- Веб-маршрут `/mesh` (flask-sock): на каждое WS-соединение — TCP к демону и
  перекачка кадров в обе стороны. Шифрование линка — от клиента до демона: веб видит
  только шифртекст.
- `deploy.sh`: libsodium (`apt`), systemd-юнит `vsc-mesh`, переменная
  `MESH_PUBLIC_URL` (например `wss://soufos.ru/mesh`), проверка апгрейда `/mesh`.

### Обмен соседями (новый тип пакета)

`PEERS = 5`, только между соседями (не ретранслируется): body — UTF-8 строки
`wss://…`, разделённые `\n`, не больше 16 адресов по ≤ 200 байт; `ttl = 0`.
Публичный узел шлёт новому соседу свой `MESH_PUBLIC_URL` и известные ему адреса.
Клиент запоминает адреса (настройки, не больше 32) и держит соединения с
`MESH_LINKS = 3` узлами: стартовые первыми, затем выученные; обрыв — повтор с
backoff 2 с … 2 мин. Векторы пополняются кодированием `PEERS`.

### Стартовые узлы

По умолчанию — `wss://<сервер>/mesh`, где сервер — адрес «Центра» из настроек
(домен сменится — адрес не хардкодится). В настройках можно добавить свои адреса.

### Выбор пути канала

`P2PService` при подключении канала (новый и переподключение) запускает параллельно:
рандеву через сервер (как сейчас) и `mesh.find(tagKey(prs))`.
- Пара через сервер приходит обоим почти одновременно (её выдаёт сервер), поэтому
  сервер в приоритете: если mesh нашёл собеседника первым, ждём ещё `MESH_GRACE = 3 с`
  пары от сервера; не пришла — канал идёт через mesh, рандеву на сервере отменяется.
- Сервер недоступен (заблокирован, нет интернета) — его попытка падает, канал идёт
  через mesh без ожидания.
- Редкая гонка на границе ожидания (у одной стороны сервер, у другой mesh) лечится
  существующим переподключением: рукопожатие не пройдёт по таймауту → новая попытка.
- Прямой WebRTC поверх mesh не поднимается (сигналинг сейчас через relay-сервер) —
  YAGNI; канал через mesh остаётся через mesh.

Статус канала: «напрямую» / «через сервер» / «через mesh».

### Настройки

«Mesh-сеть» (вкл.; выключено — узел не создаётся), «Ретрансляция для других» (вкл.),
«Узлы mesh» (список адресов). Десктоп — в окне настроек, телефон — в разделе «Mesh».

## Этап 3. Android-радио и раздел «Mesh»

### BLE (по умолчанию, в фоне)

- GATT-сервис МЫС (свой UUID), характеристика записи (RX) и уведомлений (TX).
  Каждый телефон одновременно реклама+GATT-сервер и сканер+GATT-клиент; к соседу
  подключается тот, у кого меньше случайный id в рекламе (одна связь на пару).
- Кадр линка режется на куски по MTU: `u8 флаги (1 = последний) ‖ данные`;
  сборка до `MAX_FRAME`. MTU запрашивается 517.
- Работает, пока жив `MysService` (уже foreground); разрешения
  `BLUETOOTH_SCAN/CONNECT/ADVERTISE` (API 31+) или геолокация (API ≤ 30) —
  запрашиваются в разделе «Mesh» при включении.
- Скорость — килобайты/с: текст идёт, файлы медленно.

### Wi-Fi Direct (пока открыт раздел «Mesh»)

`WifiP2pManager`: обнаружение сервиса МЫС, группа, `TcpWire` между участниками
(владелец группы слушает порт, остальные подключаются). Выключается при уходе с
экрана — Wi-Fi Direct держит радио и мешает обычному Wi-Fi.

### Раздел «Mesh» (телефон)

Переключатели «Mesh-сеть», «Ретрансляция», «Bluetooth», статус: соседей по каждому
проводу, активных маршрутов, переслано для других; список узлов; при открытом
экране — Wi-Fi Direct и его соседи.

### Проверка

- Этап 2: интеграционные тесты десктоп↔демон↔телефон через локальный vsc_web
  (`/mesh` → демон); выбор пути — сервер выключен → канал через mesh; сервер есть →
  через сервер; PEERS-векторы.
- Этап 3: нарезка/сборка кадров BLE — юнит-тесты; само радио — на реальных телефонах
  (эмулятор BLE/Wi-Fi Direct не даёт), чек-лист для владельца.

## Чек-лист на реальных телефонах (этап 3)

Эмулятор не даёт BLE между устройствами и Wi-Fi Direct — проверяется вручную:

1. Два телефона, на обоих МЫС, Bluetooth включён; «Настройки → Mesh» — выдать разрешения.
   Через ~10 с: «Bluetooth: 1 соседей» на обоих.
2. Включить авиарежим + Bluetooth на обоих (интернета нет). Канал P2P по общей фразе →
   статус «В сети · через mesh», сообщения ходят. Файл до 100 КБ доходит (медленно).
3. Свернуть приложение (фон включён) — сообщение с другого телефона приходит уведомлением.
4. Wi-Fi Direct: на обоих открыт раздел «Mesh» → «Wi-Fi Direct: 1 соседей» (Android может
   спросить подтверждение подключения). Уход с экрана — группа распадается.
5. Три телефона цепочкой (A и C вне досягаемости друг друга): канал A↔C через B,
   у B растёт «Переслано для других». Выключить у B «Ретрансляцию» и разблокировать
   заново — канал A↔C больше не находится.
6. С интернетом: после деплоя сервера «Интернет-узлы: 1»; при недоступном /p2p канал
   уходит в mesh через публичный узел.
