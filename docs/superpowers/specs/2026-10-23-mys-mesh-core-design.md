# МЫС Mesh — этап 1: ядро протокола

Дата: 2026-10-23. Статус: согласовано с владельцем проекта.

## Зачем

Mesh-сеть — ещё один путь для существующих P2P-каналов МЫС (по секретной фразе),
кроме прямого WebRTC и relay через сервер soufos.ru. Сообщения идут через соседние
узлы МЫС: рядом (Bluetooth LE, Wi-Fi Direct) и через интернет. Сервер для этого
не нужен; если его заблокируют, каналы продолжат работать через mesh.

Решения владельца:

- единый протокол для локальных соседей и интернет-узлов;
- **только живой маршрут**: чужие узлы ничего не хранят, store-and-forward нет;
- ретранслирует любой узел МЫС; ретрансляцию для чужих можно выключить настройкой;
- по mesh идут **те же P2P-каналы** (CPace + Double Ratchet не меняются);
- маршрутизация **по запросу** (в духе AODV), не flooding и не DHT;
- старт в интернете — список стартовых узлов (soufos.ru — один из них) + обмен соседями.

## Этапы

1. **Ядро протокола (этот документ):** шифрование линка, формат пакетов,
   маршрутизация, точка встречи с сессией; Kotlin и Python; симулятор в тестах.
2. Интернет-узлы: TCP/WebSocket-линки, стартовые узлы, обмен соседями, узел на
   soufos.ru, выбор пути в канале (напрямую / mesh / сервер).
3. Android-радио: BLE (фон, по умолчанию), Wi-Fi Direct (пока открыт раздел «Mesh»),
   раздел «Mesh» в UI, переключатель ретрансляции.
4. (Опционально) Bluetooth на десктопе.

В этапе 1 нет: радио, интернет-узлов, UI, выбора пути в канале.

## Архитектура

| Сторона | Где | Зависимости |
|---|---|---|
| Android | модуль `:mesh` (чистый Kotlin/JVM, корутины) | `:crypto` (libsodium через lazysodium), `:p2p` — только интерфейсы `Transport`/`Role` |
| Десктоп | пакет `mys_mesh` (asyncio) | `mys_crypto`, `mys_decentralized` — только интерфейсы |

Эталон байтов — десктоп; совместимость — тест-векторами (`tools/gen_vectors.py`).
Ядро не открывает сокетов и не знает о радио, UI и хранилище.

Три слоя:

1. **Link** — соединение с одним соседом поверх «провода» (упорядоченный надёжный
   поток кадров). Делает шифрование линка. Провода этапа 1: `MemoryLink` (тесты),
   `TcpLink` (тест совместимости; основа этапа 2).
2. **Router** — RREQ/RREP/DATA/RERR, таблицы в памяти, лимиты.
3. **MeshRendezvous** — `find(tagKey) → (Role, Transport)`: тот же контракт, что
   у рандеву через сервер. `Session`, `handshake`, Ratchet, файлы — без изменений.

### Интерфейс

- `MeshNode(config)`; `config`: `relay: Boolean = true`, лимиты и таймауты ниже.
- `attach(wire)` / `detach(wire)` — провод приносит соединение, ядро делает
  рукопожатие линка и включает соседа в маршрутизацию.
- `find(tagKey, timeout) → (Role, Transport)`; таймаут — `TimeoutException`
  (Kotlin) / `asyncio.TimeoutError` (Python).
- `stats()` — число соседей, активных маршрутов, переслано байт для других.

## Ключи и метки

Канал хранит `prs` (вход CPace; на сервер не уходит). Из него:

```
tag_key = HKDF-SHA256(ikm = prs, salt = "", info = "mys-mesh-tag-key", L = 32)
hour    = floor(unix_time_seconds / 3600)
tag     = BLAKE2b(digest = 32, key = tag_key, person = "mys-mesh-tag",
                  data = u64be(hour))
```

- Выводится из `prs`, а не из `room_id`: `room_id` видит сервер, и он мог бы
  вычислять метки. Вывод из `prs` есть и при переподключении без фразы.
- Принимаются метки текущего и предыдущего часа (расхождение часов).
- Метка в RREQ — единственное, что связано с каналом; связать её между часами
  без `prs` нельзя.

## Шифрование линка

Над проводом — кадры `u32be длина ‖ байты` (длина ≤ 72 KiB, иначе разрыв).

1. Каждая сторона генерирует временную пару X25519 (`crypto_kx_keypair`) и шлёт
   открытый кадр `"MYSM" ‖ u8 версия (=1) ‖ pk (32)`. Неверная магия/версия — разрыв.
2. Роль `crypto_kx`: «клиент» — сторона с лексикографически меньшим `pk`; равные
   `pk` — разрыв. `crypto_kx_client/server_session_keys` → `rx`, `tx`.
3. Каждая сторона: `crypto_secretstream_xchacha20poly1305_init_push(tx)` и шлёт
   заголовок (24 байта) отдельным кадром; принимает заголовок соседа → `init_pull(rx)`.
4. Дальше каждый mesh-пакет — одно сообщение secretstream (тег MESSAGE).
   Ошибка расшифровки, тег FINAL или повтор — разрыв линка.

Постоянной личности узла нет. Подмена соседа возможна (нет аутентификации);
содержимое защищено сквозным шифрованием канала, линк скрывает метки от
пассивного наблюдателя эфира.

## Mesh-пакет

Все целые — big-endian.

```
u8  version   = 1
u8  type      1 RREQ | 2 RREP | 3 DATA | 4 RERR
u8  ttl       остаток прыжков (RREQ); 0 в остальных
u8  hops      пройдено прыжков (информационно)
16  id        RREQ: id запроса; RREP: id запроса, на который ответ;
              DATA/RERR: id маршрута
... body
```

| Тип | body |
|---|---|
| RREQ | `tag (32) ‖ nonce (16)` |
| RREP | `route_id (16) ‖ nonce (16)` |
| DATA | кадр сессии (0…65 600 байт; пустой — keepalive) |
| RERR | пусто |

Пакет длиннее 65 600 + 20 байт, неизвестный тип/версия или неверная длина body —
разрыв линка с этим соседом.

## Маршрутизация

Константы (настраиваемые в `config`, значения по умолчанию):

| | |
|---|---|
| `TTL_MAX` | 8 |
| `DEDUP_TTL` | 120 с, не более 4096 записей (вытеснение старых) |
| `ROUTE_IDLE` | 120 с без DATA — маршрут удаляется; не более 1024 маршрутов |
| `KEEPALIVE` | 30 с — конечная точка шлёт пустой DATA |
| `RREQ_RETRY` | 5 с — повтор поиска с новым id, пока не найден или таймаут |
| `RREQ_RATE` | 10 RREQ/с от одного соседа, лишние отбрасываются |
| `RELAY_RATE` | 256 KiB/с суммарно на DATA чужих маршрутов, лишнее отбрасывается |

**Поиск.** `find(tagKey)`: узел регистрирует «ожидание» с меткой текущего часа
(и предыдущего) и случайным `nonce`, рассылает RREQ (`ttl = TTL_MAX`, новый id)
всем соседям, повторяет каждые `RREQ_RETRY`.

**Получен RREQ** от соседа N:

1. id уже видели — отбросить. Иначе запомнить `id → N` (обратный путь).
2. Метка совпадает с ожиданием этого узла:
   - если `own.nonce < req.nonce` (побайтово) — ответить RREP (`route_id` случайный);
     этот узел — **RESPONDER**;
   - иначе (включая равные nonce) — молча поглотить (ответит другая сторона на наш
     RREQ); не ретранслировать.
   - Ответивший RESPONDER сразу снимает своё ожидание: `find` возвращается, не дожидаясь
     подтверждения доставки RREP. Если RREP потерян, рукопожатие сессии не пройдёт по
     таймауту и канал переподключится, как сейчас.
3. Иначе, если `relay` включён и `ttl > 1` — разослать всем соседям, кроме N, с
   `ttl − 1`, `hops + 1`. Иначе отбросить.

Ретрансляторы не отвечают за других и не кэшируют «где какая метка».

**Получен RREP** (id запроса X) от соседа M:

- X — наш запрос: первый RREP → маршрут `route_id ↔ M`, этот узел — **INITIATOR**,
  `find` возвращается. Последующие RREP на тот же поиск — отправить RERR по их
  `route_id`.
- X — чужой, есть обратный путь `X → N`: создать маршрут `route_id: N ↔ M`
  (если `relay` включён) и переслать RREP в N. Нет обратного пути — отбросить.

**DATA** по `route_id`: пришло от одной стороны маршрута — переслать на другую;
конечная точка отдаёт payload в `Transport.recv()` (пустой — keepalive, не отдаётся).
Неизвестный маршрут — отбросить.

**Обрыв.** Линк с соседом пропал → по всем маршрутам через него RERR в другую
сторону, маршруты удалить. Получен RERR → переслать в другую сторону и удалить;
конечная точка: `Transport.recv()` бросает `TransportException`. Сессия реагирует
как на разрыв relay сейчас (переподключение, исходящие ждут в outbox).

**Роли** совпадают с рандеву через сервер: INITIATOR (чей запрос получил ответ)
шлёт «прайм»-кадр, дальше CPace → CONFIRM → Ratchet без изменений.

**Ретрансляция выключена**: узел не пересылает чужие RREQ/RREP/DATA/RERR;
свои поиски и маршруты работают.

## Транспорт для сессии

`MeshTransport(route)`: `send(frame)` → DATA; `recv()` ← DATA этого маршрута;
`close()` → RERR и удаление маршрута. Конечная точка шлёт keepalive каждые
`KEEPALIVE`, пока транспорт открыт.

## Тестирование

1. **Векторы** (Python → `crypto/src/test/resources/vectors.json` → Kotlin):
   `tag_key(prs)`, `tag(tag_key, hour)` для нескольких часов, кодирование и разбор
   всех четырёх типов пакетов.
2. **Линк:** рукопожатие через `MemoryLink`; отказ на повреждённом, повторённом,
   слишком длинном кадре, неверной магии.
3. **Симулятор** (одинаковые сценарии на обеих сторонах, узлы и `MemoryLink` в памяти):
   - цепочка из 6 узлов: концы находят друг друга, проходят настоящий
     `handshake` (CPace, Ratchet) и обмениваются текстом;
   - кольцо и сетка: каждый узел ретранслирует каждый RREQ не больше одного раза;
   - обрыв посередине: RERR, новый маршрут, сессия продолжается;
   - одновременный поиск: ровно один маршрут, роли INITIATOR/RESPONDER;
   - собеседника нет / TTL исчерпан: `find` — таймаут;
   - флуд-узел: лимиты срабатывают, честный обмен проходит;
   - `relay = false`: чужое не пересылается, свои каналы работают.
4. **Совместимость:** Kotlin-узел ↔ Python-узел через `TcpLink` на localhost
   (`DESKTOP_PYTHON`, как интероп P2P; без переменной — пропуск).

Готово, когда: векторы совпадают, сценарии зелёные на обеих сторонах, интероп
проходит рукопожатие и обмен сообщениями, существующие тесты P2P не сломаны.

## Риски

- Злонамеренный ретранслятор может выбрасывать DATA (сессия перестроит маршрут) и
  сопоставлять время пакетов (защита от анализа трафика — вне задачи).
- Открытая ретрансляция расходует батарею и трафик — ограничено `RELAY_RATE` и
  выключателем.
